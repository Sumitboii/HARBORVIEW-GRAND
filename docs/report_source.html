Section 1

Assignment Overview

The assignment required building a full-stack AI-powered Hotel Guest Assistant — a chat interface where hotel guests can interact naturally with hotel services.

Core capabilities required:

  • Ask natural-language questions about hotel policies, amenities, rooms, and services
  • Check live room availability using a structured date/guest form
  • Hold multi-turn conversations with context carried across messages
  • Receive grounded, hallucination-free answers from a hotel knowledge base

Required Questions to Handle

#QuestionType
1What time is check-in?FAQ / Policy
2Does the hotel have a swimming pool?Amenity
3Which room is suitable for three guests?Room Info
4Is breakfast included?Policy
5What is the cancellation policy?Policy
6Do you have rooms available for a given date?Availability

All six are fully implemented and tested end-to-end.

Section 2

What Was Built

Harborview Grand AI Concierge — a two-panel luxury hotel assistant with a left sidebar showing live hotel info and shortcuts, and a right chat panel powered by Google Gemini.

Key Features Delivered

  • Natural language Q&A — Guests type any question; the system retrieves relevant hotel knowledge and generates a natural response via Gemini.
  • Room availability checker — Structured form for check-in/check-out dates and guest count; returns real-time per-room inventory.
  • Multi-turn conversation — Conversation ID maintained across messages; follow-up questions use prior context automatically.
  • Hallucination prevention — LLM grounded strictly in retrieved facts; availability numbers never pass through the LLM.
  • Graceful fallbacks — Works without any API key (KB fallback mode); API errors handled silently.
  • Intent detection — Keywords and patterns route messages to the correct handler before any LLM call.
  • Interactive sidebar — Every section (schedule, dining, amenities, contact) triggers a targeted chat query on click.
  • Hydration-safe UI — SSR/client timestamp mismatch resolved with suppressHydrationWarning and useEffect-based injection.
  • Deployed on Render — Backend and frontend as separate services via render.yaml Blueprint.

Request Lifecycle

  1. Guest submits message via chat input or sidebar shortcut click
  2. Frontend sends POST /api/chat with { message, conversationId? }
  3. Backend validates — empty message returns 400 INVALID_REQUEST
  4. Intent detection — detectIntent() classifies the message:
    • greeting / gratitude → immediate reply, no LLM call
    • booking_request → acknowledgement using conversation context
    • availability → availability handler if dates present
    • availability_needs_details → prompt for dates/guest count
    • general_question → retrieve + LLM path
  5. Retrieval — keyword-scores all KB chunks; top matches sent as LLM context
  6. LLM call — Gemini generates answer; on failure silently falls back to mockAnswer()
  7. Conversation stored — turn appended to in-memory store by conversationId
  8. Structured JSON response returned → frontend renders as bubble or availability card
Section 6

Backend Deep Dive

intentService.js — Intent Classification

IntentTrigger Keywords / Patterns
greetinghi, hello, hey, good morning/evening
gratitudethank you, thanks, great, awesome
booking_requestbook, reserve, I want a room
availabilityavailability keywords + valid dates in message
availability_needs_detailsavailability keyword, no dates present
general_questioneverything else

Why keyword-based? Intent is binary and structured. Regex is deterministic, fast, and unit-testable — AI would add non-determinism for no gain.

retrievalService.js — Knowledge Base Retrieval

TF-IDF-style keyword overlap scoring: tokenises the question, scores each KB chunk by overlap count, returns top-N chunks above threshold as LLM grounding context.

Why not embeddings? The KB has ~15 facts. Embeddings add a vector DB, extra API call, and model dependency for zero accuracy gain at this scale.

llmService.js — Gemini Integration + Fallback

callLLM(question, contextChunks, conversationHistory)
 ├ System prompt restricts model to provided hotel data only
 ├ Last 10 conversation turns sent as message history
 ├ Calls Gemini API (models/gemini-2.0-flash)
 ├ On 429 / 503 / timeout → fallback to mockAnswer()
 └ Returns { text, usedFallback, source }

availabilityService.js — Room Inventory

Fully deterministic — validates dates, computes nights, returns fixed inventory. The LLM never sees inventory numbers.

conversationStore.js

In-memory Map: conversationId → [{ role, content }]. Keeps last 10 turns per session. Resets on server restart — intentional for demo scope.

AI Integration

Model Used

Google Gemini 2.0 Flash (models/gemini-2.0-flash). Chosen for its free tier (20 req/day), strong instruction-following critical for context grounding, and fast response times. The app runs fully without an API key via KB fallback — zero credentials required for reviewers.

Where AI Is and Is Not Used

TaskAI?Reason
Intent detectionNoDeterministic; regex is faster and testable
KB retrieval scoringNoKeyword overlap — sufficient at 15-fact scale
Date / guest validationNoPure arithmetic
Room availability calculationNoDeterministic business logic
Natural-language answer generationYesOnly task requiring fluent prose output
Availability result formattingNoStructured data inserted directly into response

cannot be found in the provided information, say you don't have

Hotel Information:

Fallback Chain

Guest question
  → Retrieve KB chunks
  → No chunks match   → "I don't have that information" (no LLM)
  → Chunks found      → Call Gemini API
      Gemini succeeds → Return LLM response
      Gemini fails    → mockAnswer() from KB chunks (silent)

Section 13

Design Decisions & Trade-offs

Why Two-Column Layout?

A sidebar + chat panel mirrors real hotel concierge apps. Hotel context stays permanently visible while the chat remains focused. Each sidebar item triggers a precise chat query on click, reducing friction for the most common guest questions.

Why Keep Availability Deterministic?

LLMs can hallucinate numbers. A guest making a booking decision based on wrong room inventory would be a serious UX failure. Availability is a pure function — same input always produces the same output — and the LLM never touches inventory data at any point in the pipeline.

Why Keyword Retrieval Over Embeddings?

The KB has ~15 facts. Embeddings would require a vector database, an extra API call per query, and a model dependency for zero accuracy improvement at this scale. Keyword overlap is faster, cheaper, fully deterministic, and passes unit tests reliably. At production scale with hundreds of entries, embeddings become worthwhile.

Why In-Memory Conversation Store?

A real database requires schema migrations, connection management, and deployment setup for a demo project. The trade-off is explicit: conversations reset on server restart — acceptable for assignment scope, noted clearly in the README as a known production gap.

Why Gemini Instead of Another LLM?

Gemini 2.0 Flash offers a free tier (20 req/day), strong instruction-following, and low latency. Critically, the app works fully without any API key via KB fallback — graders and reviewers can evaluate the entire system with zero credentials.

Why suppressHydrationWarning for Timestamps?

Next.js SSR (Node.js) and the browser both call toLocaleTimeString() but return different case formats (am vs AM) due to locale differences between environments. suppressHydrationWarning on the timestamp <span> is React's recommended minimal fix for dynamic time displays — no full SSR disable needed.

Section 14

How to Run Locally

Prerequisites

  • Node.js 18 or higher
  • npm
  • Optional: a Gemini API key (the app works fully without one)

1. Start the Backend

cd backend
npm install
cp .env.example .env
# Optional: edit .env and add GEMINI_API_KEY=your_key
npm run dev
# Server listening on http://localhost:4000

2. Start the Frontend

cd frontend
npm install
cp .env.example .env
# .env sets NEXT_PUBLIC_BACKEND_URL=http://localhost:4000
npm run dev
# Open http://localhost:3000 in your browser

3. Run the Test Suites

# Backend -- 27 Jest tests
cd backend && npm test

# Frontend E2E -- 4 Playwright tests (both servers must be running)
cd frontend && npm run test:e2e
